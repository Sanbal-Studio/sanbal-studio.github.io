# Sanbal Studio 앱 포트폴리오 허브 PRD

## 1. 배경

Sanbal Studio는 여러 앱을 개발하고 운영한다. 앱이 추가될 때마다 별도 사이트를 만들면 도메인, 지원 URL, 개인정보처리방침, 앱 소개 페이지를 반복해서 관리해야 한다.

이 PRD는 `sanbal-studio.github.io`를 Sanbal Studio의 단일 앱 소개·지원 허브로 정의한다. 하나의 정적 사이트 안에서 앱 목록, 앱별 상세 정보, 앱별 지원 페이지, 앱별 개인정보처리방침을 일관된 구조로 제공한다.

참고 방향은 [Not Boring](https://notbor.ing/)처럼 독립 앱 스튜디오의 개성을 보여주는 사이트다. 다만 구체적인 시각 디자인, 컬러, 타이포그래피, 레이아웃 톤은 이 PRD 이후 별도 디자인 단계에서 확정한다.

## 2. 목표

- Sanbal Studio와 제공 앱을 한 사이트에서 소개한다.
- 앱별 상세 페이지를 App Store/Google Play 방문 전의 제품 정보 페이지로 제공한다.
- App Store/Google Play 제출에 사용할 수 있는 앱별 Support URL과 Privacy Policy URL을 제공한다.
- 앱 추가 시 새 사이트를 만들지 않고 메타데이터와 MDX 콘텐츠 추가만으로 페이지를 확장한다.
- 첫 출시 범위인 `Not Todo`, `Walk Bingo`를 같은 구조 안에서 관리한다.

## 3. 범위

### 포함

- 홈 페이지
- 앱별 상세 페이지
- 앱별 지원 페이지

- 공통 Contact 페이지
- Thread 계정 링크
- X 계정 링크
- 문의 이메일 정보
- 앱 아이콘, 앱 소개 문구, 설명, 스크린샷, App Store 링크, Google Play 링크, 개인정보처리방침 링크

### 제외

- 최종 비주얼 디자인 확정
- CMS 또는 관리자 화면
- 블로그/뉴스
- 다국어
- 서버 API
- 문의 폼 서버 처리
- 앱 분석/트래킹
- 유료 상품/결제
- 자동 스토어 메타데이터 동기화

## 4. 첫 출시 앱

첫 출시 범위에는 다음 앱을 포함한다.

- `Not Todo`
- `Walk Bingo`

앱별 공개 상태는 콘텐츠 데이터에서 관리한다. 공개 앱은 다운로드 링크를 표시하고, 준비 중 앱은 다운로드 CTA 대신 준비 중 상태를 표시한다.

## 5. 페이지 구조

### `/`

홈 페이지다. Sanbal Studio의 짧은 소개, Thread/X/이메일 링크, 앱 컬렉션을 보여준다. 방문자가 앱 목록을 빠르게 훑고 각 앱 상세 페이지로 이동할 수 있어야 한다.

### `/apps/[slug]`

앱 상세 페이지다. 앱스토어의 앱 페이지처럼 짧은 소개 문구, 앱 아이콘, 설명, 스크린샷, 주요 기능, App Store/Google Play 링크, 지원 페이지 링크, 개인정보처리방침 링크를 제공한다.

### `/apps/[slug]/support`

앱별 지원 페이지다. App Store/Google Play 제출용 Support URL로 사용한다. 앱 이름, 문의 이메일, 자주 묻는 질문, 문의 전 확인할 내용, 오류/피드백 제보 안내, 개인정보처리방침 링크를 포함한다.

App Store Connect의 Support URL은 앱 버전 메타데이터에 포함되며, 실제 연락 수단으로 이어지는 지원 웹사이트여야 한다. 따라서 공통 Contact 페이지만 제출하기보다 앱별 지원 페이지를 제출용 URL로 사용한다. 관련 기준은 Apple의 [Platform version information](https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information) 문서를 따른다.

### `/apps/[slug]/privacy`

앱별 개인정보처리방침 페이지다. App Store/Google Play 제출용 Privacy Policy URL로 사용한다. 앱별 수집 정보, 이용 목적, 보관/삭제, 제3자 제공, 문의처를 설명한다.

### `/contact`

Sanbal Studio 전체 문의 허브다. 공통 이메일, Thread, X 링크를 제공하고, 앱 관련 문의는 각 앱별 지원 페이지로 유도한다.

## 6. 콘텐츠 모델

앱 콘텐츠는 공통 메타데이터와 MDX 문서를 조합해 관리한다.

### 앱 공통 메타데이터

- `slug`: URL 식별자
- `name`: 앱 이름
- `status`: `published`, `comingSoon` 등 공개 상태
- `tagline`: 앱스토어식 짧은 소개 문구
- `summary`: 홈/목록에서 쓰는 짧은 설명
- `icon`: 앱 아이콘 이미지 경로
- `screenshots`: 앱 스크린샷 이미지 목록
- `appStoreUrl`: App Store 링크. 값이 없으면 버튼을 숨긴다.
- `googlePlayUrl`: Google Play 링크. 값이 없으면 버튼을 숨긴다.
- `supportUrl`: 내부 앱별 지원 페이지 경로
- `privacyUrl`: 내부 앱별 개인정보처리방침 경로

### 앱별 MDX 콘텐츠

- 앱 상세 MDX: 소개 문구, 긴 설명, 핵심 기능, 스크린샷 설명
- 지원 MDX: 앱별 FAQ, 문의 전 확인할 내용, 오류/피드백 제보 안내
- 개인정보처리방침 MDX: 앱별 수집 정보, 이용 목적, 보관/삭제, 제3자 제공, 문의처

앱을 추가할 때는 메타데이터 1건과 앱별 MDX 3종을 추가한다. 이 추가만으로 홈, 상세, 지원, 개인정보처리방침 페이지가 정적으로 생성되어야 한다.

## 7. 사용자 흐름

1. 방문자는 홈에서 Sanbal Studio의 소개와 앱 목록을 확인한다.
2. 관심 있는 앱을 선택해 앱 상세 페이지로 이동한다.
3. 앱 상세에서 앱스토어식 소개 문구, 스크린샷, 설명을 확인한다.
4. 앱을 설치하려면 App Store 또는 Google Play 링크로 이동한다.
5. 문제가 있거나 피드백이 있으면 앱별 지원 페이지로 이동한다.
6. 개인정보 처리 내용을 확인하려면 앱별 개인정보처리방침 페이지로 이동한다.
7. 앱과 무관한 전체 문의는 `/contact`에서 처리한다.

## 8. 상태 처리

- 스토어 링크가 없는 앱은 해당 버튼을 숨긴다.
- `comingSoon` 앱은 다운로드 버튼 대신 준비 중 상태를 표시한다.
- 스크린샷이 없는 앱은 스크린샷 섹션을 숨긴다.
- 존재하지 않는 앱 slug는 404로 처리한다.
- 앱별 지원 페이지의 이메일 링크는 앱 이름이 포함된 제목으로 연결할 수 있어야 한다.

## 9. 기술 요구사항

- 현재 저장소의 Astro 정적 사이트 전제를 유지한다.
- 앱 상세, 지원, 개인정보처리방침은 MDX 기반 콘텐츠로 관리한다.
- 앱 공통 정보는 타입이 있는 데이터 구조로 분리한다.
- 빌드 시 각 앱의 상세/지원/개인정보처리방침 경로가 정적으로 생성되어야 한다.
- GitHub Pages 배포 흐름을 유지한다.
- `pnpm build`가 배포 전 검증 기준이다.
- 페이지별 SEO 기본 메타데이터를 제공한다.
- 링크 텍스트, 이미지 대체 텍스트, 키보드 이동 가능한 구조를 접근성 최소 기준으로 둔다.

## 10. 성공 기준

- 방문자가 홈에서 Sanbal Studio와 제공 앱을 이해할 수 있다.
- 앱 상세 페이지가 스토어로 이동하기 전 충분한 앱 소개 페이지 역할을 한다.
- 각 앱은 스토어 제출에 사용할 수 있는 내부 Support URL과 Privacy Policy URL을 갖는다.
- 앱 추가 시 새 사이트를 만들지 않고 메타데이터와 MDX 콘텐츠 추가만으로 페이지가 확장된다.
- `Not Todo`, `Walk Bingo`가 같은 구조 안에서 관리된다.
- 디자인 확정 전에도 정보 구조와 콘텐츠 요구사항만으로 구현 계획을 세울 수 있다.
- `pnpm build` 기준으로 정적 사이트 빌드가 성공한다.
